## Ground rules for all workers

1. The interface contract **wins over improvisation**. A worker who believes
   the contract is wrong stops and escalates; it never renames silently.
2. Each plan's tasks carry a **Suggested agent** tier (haiku/sonnet/opus).
   The orchestrator dispatches per-task workers at that tier; when in doubt,
   go one tier up, never down, for anything touching auth, money, tokens, or
   the CAS path.
3. Every task ends green: `npm run lint`, `npx tsc --noEmit`, and its unit
   tests under `tests/unit/**` (the only suite CI runs) before commit.
4. One ticket = one branch = one PR. Plans use conventional commits tagged
   with their ticket ID.

## Dependency graph and waves

```text
Wave 1:  A  (domain + migrations)               ── no deps
Wave 2:  B  (service + APIs)   ─┐  both branch from merged A;
         E  (customer status)  ─┘  E may run in parallel with B
Wave 3:  C  (shipping email)                    ── needs A+B merged
Wave 4:  D  (admin queue)                       ── needs B+C merged; E merged (CARRIER_LABELS)
Wave 5:  F  (legacy hardening)                  ── needs B+D merged (deploy order!)
Wave 6:  G  (QA + rollout runbook)              ── needs A–F merged; human-gated
```

Merge order: **A → B → E → C → D → F → G.**

Strictly serial execution (A, B, C, D, E, F, G) is also valid and is the
safest choice for fully unattended `/ccmagic:auto-ticket` runs — the only
parallelism on offer is B∥E in Wave 2.

⚠️ **F must not deploy before D.** Until D removes the admin UI's legacy
`PUT /api/orders` shipment path, F's 400s would break the existing inline
editor. The F plan header carries this dependency.

## How to run

**Per-ticket auto (recommended):** create Linear issues BMC-216A…G (BMC team,
BeauTeas project), each linking its plan file and the interface contract,
then per wave:

```text
/ccmagic:auto-ticket BMC-216A     # wave 1
/ccmagic:auto-ticket BMC-216B     # wave 2 (optionally BMC-216E in a second session/worktree)
…
```

**In-session subagent-driven:** open the ticket's plan and follow
`superpowers:subagent-driven-development` — one fresh subagent per task at
the task's suggested tier, orchestrator reviews between tasks.

**G is different:** it is a human-gated runbook. Do not hand it to
unattended automation; every `[HUMAN GATE]` step needs explicit confirmation.

## Escalation triggers (stop conditions baked into the plans)

- Contract/codebase mismatch that would force a rename → stop, escalate.
- B/C/E preflights: upstream ticket's exports absent or shaped differently →
  stop (do not re-implement upstream work).
- E: `orders.shipping_carrier` missing (0022 not applied locally) → stop.
- Any test that can only pass by weakening an acceptance criterion → stop.
