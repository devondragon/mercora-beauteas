# BMC-216: Basic Order Management and Fulfillment Plan

**Status:** Ready for implementation  
**Date:** 2026-07-30  
**Ticket:** BMC-216  
**Target:** A lightweight, single-operator fulfillment workflow with Shopify/WooCommerce-level basics, not an enterprise OMS

## Summary

BeauTeas needs a reliable workflow for turning a paid order into a shipped
order. The first production order confirmed that the operator currently depends
on payment and merchant-notification emails, then manually inspects the admin
area without a coherent fulfillment workflow.

The repository already contains partial fulfillment functionality:

- `orders` has status, tracking number, and shipment/delivery timestamps.
- The admin order list exposes inline status, carrier, and tracking edits.
- A generic status-update email can render shipment information.
- Paid orders normally enter `processing`.
- The refund path owns cancellation/refund state and inventory restocking.

These pieces are not yet a safe OMS. The generic order update endpoint permits
invalid transitions, trusts browser-supplied shipment timestamps and tracking
URLs, has no guarded shipment transition, and cannot clearly report or retry
shipping-email failures. Admin filtering is also applied only to the currently
loaded page after the API has loaded all orders.

V1 will consolidate these dormant pieces behind one dedicated, concurrency-safe
shipment workflow.

## Product Decisions

The following decisions were made while scoping BMC-216:

1. Expected volume is fewer than 10 orders/day at launch and fewer than 30/day
   after six months.
2. One operator will fulfill orders. Assignment and claiming are unnecessary.
3. The operator will purchase and print labels through Rolo using UPS and FedEx.
4. Rolo and carrier API integration are deferred.
5. Tracking is optional. When supplied, it appears in the shipping email and on
   the customer's order-status page as a carrier link.
6. V1 supports exactly one shipment and one tracking number per order.
7. Customers receive an order confirmation, a shipping confirmation, and
   existing cancellation/refund emails. They do not receive `processing` or
   manually generated `delivered` emails.
8. Packing slips and pick lists are excluded. A pick list may be reconsidered
   after operator feedback.
9. Gift-card orders receive no special automatic fulfillment behavior in this
   phase.
10. Pre-shipment cancellation continues through the existing hardened refund
    path.
11. Bulk UI and bulk API operations are deferred.
12. Fulfillment actions require an audit history.
13. For v1, `shipped` is the terminal operator-managed fulfillment state.
    `delivered` remains readable for legacy records and future carrier
    automation but is not manually managed.

## Goals

- Give the operator an accurate queue of paid orders awaiting shipment.
- Let the operator mark one order shipped with optional carrier/tracking data.
- Send the customer exactly one initial shipping confirmation with safe retry
  behavior.
- Show shipment status and tracking to registered and guest customers.
- Record who performed each fulfillment action and when.
- Preserve all existing payment, refund, and inventory invariants.
- Leave a clean boundary for a possible Rolo integration without implementing
  carrier APIs now.

## Non-Goals

V1 explicitly does not include:

- Rolo, UPS, or FedEx API integration
- Label purchasing, rate shopping, or printing
- Carrier webhooks or live package events
- Partial fulfillment, multiple parcels, or multiple tracking numbers
- Bulk fulfillment UI or API operations
- Fulfillment assignment, claiming, warehouses, or locations
- Manual delivery confirmation
- Packing slips or pick lists
- Reserved-versus-on-hand inventory
- Automatic gift-card order fulfillment
- New return, cancellation, refund, or restocking behavior
- Customer address editing after purchase

## Order Lifecycle

| Order state | Operational meaning | V1 behavior |
|---|---|---|
| `pending` + payment `pending` | Checkout draft or unpaid order | Hidden from fulfillment |
| `processing` + payment `paid` | Awaiting shipment | Operator may mark shipped |
| `shipped` + payment `paid` | Fulfilled | Tracking may be corrected; email may be resent |
| `delivered` | Legacy/future carrier state | Read-only |
| `cancelled` / `refunded` | Existing refund workflow | Read-only from the OMS |

The only new operator-owned state transition is:

```text
processing + paid ── Mark shipped ──> shipped
```

The server owns `shipped_at`. Clients cannot supply timestamps, payment state,
arbitrary tracking URLs, or a destination status.

## Architecture

```text
Admin order queue
       |
       v
Dedicated shipment API
       |
       v
Fulfillment service
  |-- validates paid + processing
  |-- validates optional carrier/tracking
  |-- performs guarded D1 status update
  `-- appends audit event via db.batch()
       |
       v
Shipping email service
  |-- sends with a deterministic idempotency key
  `-- records sent/failed audit event
       |
       |----------> Registered account order page
       `----------> Signed guest order-status page
```

### Design Principles

- `orders` remains the aggregate because V1 permits one shipment per order.
- Shipment mutation is implemented in a dedicated domain service, not directly
  in a React component or generic CRUD handler.
- All status and timestamp decisions occur on the server.
- Tracking links are derived from typed carrier data; a browser cannot persist
  an arbitrary customer-facing URL.
- The guarded order update and shipment audit event are atomic through
  `db.batch()`, the D1 multi-statement primitive.
- Email delivery is a best-effort side effect after shipment commit. Failure
  never rolls an order back from `shipped`.
- Existing money, refund-ledger, and inventory services remain the sole writers
  of their respective state.

## Data Model

### Orders

Continue using the existing fields:

- `status`
- `payment_status`
- `tracking_number`
- `shipped_at`
- `delivered_at`

Add:

```text
shipping_carrier TEXT NULL
```

Application-level carrier values:

- `ups`
- `fedex`
- `other`

Migration behavior (next free migration numbers are `0022+`):

- Add the nullable column.
- Backfill precedence: `json_extract(extensions, '$.carrier')` first, falling
  back to `shipping_method` only when it matches a known carrier token —
  `shipping_method` mostly holds real shipping methods such as `standard`, so
  an unconditional fallback would pollute the data.
- Normalization: map case-insensitive UPS/FedEx variants to `ups`/`fedex`.
  Any other non-empty value (USPS, DHL, free text) becomes `other`; empty or
  null stays null. `other` renders as a tracking number with no link.
- Do not delete `extensions.carrier`. Leaving it untouched is the lossless
  record of what `other` originally was; the migration only stops anything
  reading it.
- Do not add a `tracking_url` column.
- Stop treating `extensions.trackingUrl` as authoritative.
- Add `carrier` and `trackingUrl` to the server-owned keys that
  `mergeExtensions` strips from client extension payloads, so the old admin
  form or a stale tab cannot resurrect them.

Tracking URLs are derived at the response/email boundary from
`shipping_carrier` and `tracking_number`.

### Order Events

Add an append-oriented `order_events` table:

| Column | Purpose |
|---|---|
| `id` | Unique event ID |
| `order_id` | Owning order |
| `event_type` | Fulfillment action |
| `actor_type` | `admin`, `service`, or `system` |
| `actor_id` | Clerk user ID or API-token identity where available |
| `from_status` | Previous order status when relevant |
| `to_status` | New order status when relevant |
| `details` | JSON event metadata |
| `created_at` | Server timestamp |

Initial event types:

- `shipment_created`
- `tracking_updated`
- `shipping_email_sent`
- `shipping_email_failed`
- `shipping_email_resent`

Indexes:

- `(order_id, created_at)`
- `event_type`

JSON-mode Drizzle columns must receive raw objects rather than manually
stringified JSON.

## Domain Services

### Fulfillment Transitions

Add a dependency-free module containing the transition matrix and validation:

- An order is fulfillable only when `payment_status === "paid"` and
  `status === "processing"`.
- `pending`, `shipped`, `delivered`, `cancelled`, and `refunded` cannot be
  newly shipped.
- A repeated request with identical shipment data returns the existing
  fulfillment result.
- A second request with conflicting shipment data returns `409 Conflict`.
- Tracking correction is allowed only after shipment.
- Status reversal is not supported.

This module should be unit tested without D1, Next.js, Clerk, Resend, or
Cloudflare bindings.

### Tracking

Add a pure tracking module that:

- Normalizes carrier codes.
- Bounds and strips control characters from tracking input.
- Requires a carrier when a tracking number is supplied.
- Builds UPS and FedEx links with URL-encoded tracking numbers.
- Returns no link for absent tracking or an unsupported carrier.

Do not fall back to a Google search URL, because it exposes the tracking value
to an unrelated third party and is not a carrier-owned destination.

### Fulfillment Persistence

Add a server-only fulfillment service that:

1. Reads and validates the current order.
2. Generates server-side operation and shipment timestamps.
3. Runs a guarded update equivalent to:

   ```sql
   UPDATE orders
      SET status = 'shipped',
          shipping_carrier = ?,
          tracking_number = ?,
          shipped_at = ?,
          updated_at = ?
    WHERE id = ?
      AND status = 'processing'
      AND payment_status = 'paid'
   RETURNING *;
   ```

4. Inserts `shipment_created` conditionally under the same operation marker.
   Concretely, the event insert is
   `INSERT INTO order_events … SELECT … FROM orders WHERE id = ? AND
   status = 'shipped' AND shipped_at = ?` using this request's exact
   server timestamp (ISO 8601 with milliseconds), so the insert fires only
   when this request's update won. This is the same update-plus-audit batch
   shape as `lib/models/mach/subscriptions.ts`.
5. Executes the update and event insert with `db.batch()`.
6. When the guarded update matched zero rows, re-reads the order and
   branches:
   - order missing → `404`
   - `status = 'shipped'` and stored carrier + tracking equal the request
     after normalization → `200` with the existing shipment (idempotent
     retry)
   - `shipped` with different data → `409 shipment_conflict`
   - any other status → `409 not_fulfillable`, including the current status
     in the body so the admin UI can say why

The conditional event insert must not create a false audit entry when the
guarded update changes zero rows.

Tracking correction uses a guarded `shipped`-order update and appends
`tracking_updated` with the previous and new values.

## API Design

### Create Shipment

```http
POST /api/admin/orders/{id}/ship
Content-Type: application/json

{
  "carrier": "ups",
  "trackingNumber": "1Z..."
}
```

Both fields are optional as a pair:

- No carrier and no tracking number: valid untracked shipment.
- Tracking number without carrier: invalid.
- Carrier without tracking number: invalid unless product requirements later
  establish a useful carrier-only case.

Responses:

- `201`: shipment created
- `200`: idempotent identical retry
- `400`: malformed carrier/tracking input
- `401`/`403`: unauthorized
- `404`: order missing
- `409`: order is not fulfillable or conflicts with an existing shipment

The response includes the updated order, derived tracking link, email result,
and audit metadata.

### Update Tracking

```http
PATCH /api/admin/orders/{id}/tracking
```

- Valid only for an already shipped order.
- Updates carrier/tracking and appends `tracking_updated`.
- Does not automatically email the customer.
- Returns `409` for a stale or non-shipped order.

### Retry or Resend Shipping Email

```http
POST /api/admin/orders/{id}/shipping-email
```

The request distinguishes:

- Retry after no successful send.
- Intentional resend after a recorded successful send.

Each intentional resend receives a new event ID and idempotency key. A retry of
the same email attempt reuses its deterministic key.

### Read Audit History

```http
GET /api/admin/orders/{id}/events
```

Returns fulfillment events ordered oldest to newest. Refund-ledger details and
other server-owned extension data must not be exposed through this endpoint.

### Existing Generic Order Update

After this plan, every lifecycle transition has a dedicated owner: the
Stripe webhook (`pending → processing`), the ship endpoint
(`processing → shipped`), and the refund route (`→ cancelled`/`refunded`).
Nothing legitimate is left for a generic status write, so `PUT /api/orders`
is reduced to an explicit allowlist:

- Accepted: `notes`, `external_references`, and the (further restricted)
  extensions merge.
- Rejected with `400` naming the correct endpoint: `status`,
  `tracking_number`, `shipped_at`, `delivered_at`, `shipping_method`, and
  any tracking URL.
- The email-on-status-change block is deleted rather than guarded — with no
  status writes possible, this is what actually enforces product decision 7
  (no `processing` emails from the generic path).

The admin UI must stop using this endpoint for shipment creation. Existing
payment-status, cancellation/refund, extension-merge, and refund-ledger
protections remain intact.

## Admin Experience

### Queue

Redesign `/admin/orders` around fulfillment:

- Default view: **Awaiting shipment**
- Additional views: **Shipped**, **Cancelled/refunded**, and **All**
- Default sort: oldest first for awaiting shipment
- Search: order number, recipient, or customer email
- Server-side filtering, count, sort, and pagination
- No bulk selection

The list API must apply filters before pagination rather than filtering only the
current page in React.

### Shipment Action

The awaiting-shipment row exposes **Mark shipped**. The modal contains:

- Carrier: UPS, FedEx, or Other
- Optional tracking number
- A preview of the derived tracking link when available
- A statement that the customer will receive a shipping email
- Explicit confirmation

The success result immediately moves the order out of the awaiting queue.

If the database update succeeds but email fails:

- Keep the order shipped.
- Show a warning rather than a false overall failure.
- Expose **Retry email**.
- Record `shipping_email_failed`.

### Shipped Order

A shipped order displays:

- Shipped date
- Carrier
- Tracking number and link
- Shipping-email status
- **Edit tracking**
- **Retry email** or **Resend email**

### Audit Timeline

The existing admin order detail page gains a fulfillment-history card showing:

- Human-readable action
- Actor
- Timestamp
- Old/new carrier and tracking data when relevant
- Email success/failure state

It must not render raw event JSON.

## Shipping Email

Create a dedicated shipment-confirmation function rather than continuing to
overload the generic status email.

The email includes:

- Order number
- "Your order has shipped"
- Carrier and tracking number when supplied
- Direct carrier tracking button when supported
- Link to the BeauTeas order-status page
- A short preview of the purchased items

The email excludes:

- Internal notes
- Payment references
- Audit events
- Fabricated delivery estimates
- Live carrier state

All customer, order, item, carrier, and tracking strings must be HTML escaped.

Use deterministic Resend idempotency keys:

```text
shipping-confirmation/<order-id>/initial
shipping-confirmation/<order-id>/resend/<event-id>
```

Resend supports idempotency keys for email sends, with provider-side keys
retained for 24 hours:

<https://resend.com/docs/dashboard/emails/idempotency-keys>

The local event history is the durable record beyond that provider window.

The email function returns a typed result. Callers must inspect `success`
rather than treating a resolved promise as proof of delivery.

## Customer Order Status

### Registered Customers

Update `/account/orders/[id]` with a shipment card:

- Current status
- Shipped date
- Carrier
- Tracking number
- External carrier link

The existing ownership check remains mandatory.

### Guest Customers

Guest checkout is active in production, but guest orders currently have no
customer-accessible order-status page. Add:

```text
/order-status/{order-id}?token={signature}
```

The token is an HMAC-SHA256 bearer token modeled after the existing
unsubscribe-token implementation:

- Orders have no `email` column; the guest recipient resolves as
  `extensions.email || shipping_address.email` — exactly how the
  order-confirmation sender finds it today. Extract that resolution into a
  shared `getOrderCustomerEmail(order)` helper and sign a versioned scope of
  the form `order-status:v1:<orderId>:<normalizedEmail>` with it.
- If no email resolves, generate no guest link in the shipping email — a
  token bound to an empty string would verify for any email-less order.
- Use a dedicated `ORDER_STATUS_SECRET`.
- Do not put the customer email or address in the token.
- Fail closed when the secret is absent.
- Bound token length before decoding or verifying.
- Compare signatures without early exit.

The guest page shows only:

- Order number and placed date
- Current order status
- Shipped date
- Carrier and tracking link
- Item names and quantities

It does not show:

- Full shipping or billing address
- Payment method or PaymentIntent ID
- Internal notes or extensions
- Admin audit history
- Refund ledger contents

Add `noindex` metadata and a no-referrer policy so the bearer token is not
forwarded when a customer follows the external carrier link.

Guard the page with `PUBLIC_RATE_LIMITER` via `enforceRateLimit` keyed by
IP in the server component, returning not-found on both rate-limit and
verification failure so there is no existence oracle — consistent with the
BMC-180 convention on the other public endpoints.

## Merchant Notification

Keep the current new-order merchant notification during and after rollout. It
serves as the arrival alert; the admin queue becomes the source of truth for
fulfillment.

As a small cleanup, its **Manage this order** link should point directly to the
specific admin order rather than the unfiltered order list.

## Build-versus-Integrate Decision

**Decision:** Build the manual BeauTeas fulfillment workflow and do not
integrate Rolo or carrier APIs in V1.

Rolo remains responsible for:

- Carrier account access
- Label creation
- Label printing
- Any rate or shipment purchasing workflow

BeauTeas is responsible for:

- Paid-order queueing
- Recording shipment state
- Optional carrier/tracking capture
- Customer communication
- Customer-visible status
- Fulfillment audit history

A future Rolo integration can call the same fulfillment service after label
creation. V1 should not introduce a speculative provider framework; the domain
service and typed carrier boundary are sufficient seams.

## Definition of Done

BMC-216 V1 is complete when:

- A paid order automatically appears in the awaiting-shipment queue.
- The operator can mark it shipped with or without tracking.
- The transition is concurrency-safe and server-timestamped.
- One automatic shipping email is attempted and its result is visible.
- A failed email can be safely retried.
- Registered and guest customers can view order status.
- Supported tracking numbers link to the correct carrier site.
- Fulfillment actions have a readable audit history.
- Generic order updates cannot bypass the shipment workflow.
- Payment, refund, and inventory regression tests pass.
- Rolo/carrier integration, partial shipments, bulk operations, assignments,
  delivery automation, and print documents remain explicitly out of scope.
